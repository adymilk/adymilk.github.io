为什么是 FDE

这个问题面试第一轮就会被问，所以我把它写在前面。

我的答案不是「我看好这个方向」，而是一件具体的事。

在做 Minitab 二次开发时，我最先遇到的不是技术问题，而是一个定义问题：
「让工程师在浏览器里看到 SPC 控制图」这句话里，有多少东西是没说的？
刷新频率是多少？并发几个人？Minitab 是单机授权这意味着什么？分析口径谁定？

我当时花了远比预期多的时间在这些问题上，事后回看 —— 那段时间才是这个项目
真正的价值所在。因为约束一旦谈清楚，技术方案几乎是自然浮现的；而如果约束
没谈清楚，代码写得再漂亮也只是在猜。

那次经历让我确认了一件事：我喜欢做的不是「给我需求、我来实现」，而是
「需求和现实都对不齐，我来把能对齐的那部分变成能跑的系统」。

后来做 SPC 数据架构时又是同一类问题 —— 「把数据接进来做分析」这句话
背后是两种成本差一个量级的架构，需求方并没有说清是哪一种。

这就是 FDE（Forward Deployed Engineer）在做的事 —— 部署在客户现场，
在前线的模糊信息里划定可交付的边界。他同时需要能读懂业务、能动手实现、
并且对「什么不做」有判断力。这三件事我在工业质量方向上正好都做过。

代表案例

案例 1 · SPC 数据架构：不搬数据，搬能力

  • 约束：客户质量数据散落在 6 种数据库（SQL Server / MySQL / Oracle /
    PostgreSQL / MES / ERP）与现场侧的 SCADA / PLC / CMM / 传感器上
  • 我的方案：数据访问层 + 标准化测量事件模型，让多个分析引擎共享同一份
    标准化数据，而不是把客户数据全量复制进平台
  • 关键取舍：主动放弃传统的 ETL 全量复制（那条路更省事、工期更可估）。
    理由是客户库已有大量累积检测数据，全量复制的代价是存储翻倍、同步时效差；
    且工业现场常有「数据不出内网」的约束，复制这个默认动作在这里不成立。
    同理，多引擎各自取数虽然写起来快，但会让「口径漂移」迟早发生 ——
    而质量分析里两个系统算出不同的 CPK，是灾难。
    定下的原则是：能直接用就不搬；需要持续分析就增量；需要实时就走数据流。
  • 结果：架构演进方向与原则可核实；量化结果无法提供 —— 原始素材里
    没有留下对比基线，我不补数字
  • 证据等级：L1 展示架构方向明确；量化结果缺失
  • 完整决策链：作品与证据 · 案例 3

案例 2 · Minitab COM 桥接服务

  • 约束：Minitab 只开放 C# 的 COM 接口，而 COM 组件无法被 Web 程序直接调用
  • 我的方案：Windows 服务 + HTTP 轮询 + OrderID 异步取结果
  • 关键取舍：不在「桥接 vs 用 C# 重写分析逻辑」之间选容易的那条，
    而是选不替换客户已经信任的东西 —— 重写的隐藏代价不是几个人月的编码，
    是必须重新证明统计正确性、并让客户已有的历史报告与新系统对得上。
    调用方式同理：同步的代价（并发被 Minitab 实例数硬锁死）是不可控的，
    异步的代价（多一次状态查询）是可枚举的。
  • 结果：无法量化。 我的原始笔记里只有技术描述，没有「原来 ___ → 现在 ___」
    这类对比基线。我不会补一个听起来合理的数字上去。
  • 证据等级：L1 展示目标 L2
  • 完整决策链：FDE 的第一性问题：在写代码之前划定边界

案例 3 · 这个站 · L2 可复现站点公开可访问；构建可复现

  • 约束：需要一个能承载 FDE 求职的材料载体，而不是一个技术博客
  • 我的方案：作品前置的信息架构 + 案例按决策链组织 + 证据分级（L0–L3）
    • CI 自动构建
  • 关键取舍：下架了此前积累的 61 篇技术笔记（原文归档进 git 历史）。
    删掉自己写的东西比继续写更难，但访客的时间有限 —— 一个能让人在 20 秒内
    看到「交付过什么」的站点，比一个让人看到「写了多少篇笔记」的站点有用。
    另外，配色从亮天蓝改成深靛蓝，正文容器两套（.post-body 与
    .custompage）都做了覆盖，避免出现「文章页很专业、独立页还是博客默认样式」
    的割裂。
  • 结果：站点从「60+ 篇笔记的博客」变成「5 个页面的作品集」，
    /works/ 与 /resume/ 承担全部说服力
  • 可复现证据：npm install && npm run server；源码在
    github.com/adymilk/blog_backup
